**最佳 Agentic 奖三条核心维度：**

| 维度 | 官方要求 |
|---|---|
| **任务完成** | 从真实输入到执行与结果核验，而不止生成界面或摘要 |

- **人在回路**——重要决定留给用户，应用应呈现需要确认的事项，并清楚反馈操作结果

### 1.3 评分核心（来自 9/23 启动会 Alex 主讲）

比赛比的不是模型，是**从意图到应用的生产线（Harness/Pipeline）构建能力**：

```
用户说一句话
     ↓
意图理解（Agent 理解需求，提取财务信息）
     ↓
Autoscript 结构化（把对话结果转成结构化 UI 数据）
     ↓
Makepad 虚拟机渲染（生成可交互的财务卡片/界面）
     ↓
Agent 自驱操控（可读组件树、可操作，不是静态页面）
     ↓
记忆与状态留存（下次回来更懂你）
```

**选手角色是 Builder：搭好生产线，代码让 Agent 写。不需要懂 Rust。**

## 二、平台调研结论（来自与多个 AI 的深度讨论）

### 2.1 OctoSense 到底是什么

官方架构：

```
            OctoSense Shell
                   │
          ┌────────┴────────┐
          │                 │
      Card Runner       Octos Kernel
          │                 │
   OctoScript App       System Agent
          │                 │
          └────── App Peer ┘
```

关键事实：
- 一个 Shell 有一个 Octos kernel
- 每个 App / account 有自己的 app agent peer
- App 有自己的 workspace、memory、transcript
- Script App 通过 `host.request("octos.*")` 接触自己的 Agent
- App 本身**不能直接碰 kernel**
- Agent 的权限、工具调用和审批由 Shell 管理

**不是"可以运行 HTML/JS 小程序的平台"，而是"一个把 App、状态、Agent、权限和系统交互放在一起的 Agent Shell"。**

### 2.2 关键时间差（最重要的发现）

官方已经把 App 自己的 Agent 架构设计好了（`AGENT.md`、`tools.json`、`skills`、`triggers`、`background`、`glance`），但**不同部分的落地状态不同**：

| 能力 | 当前状态 | 对兜兜的含义 |
|---|---|---|
| `fs.*` | ✅ 完全可用 | 本版已用（state.json 持久化） |
| `Timer` | ✅ 完全可用 | 本版轻量用（App 打开重算） |
| `model.complete` | ⚠️ 可用但有限（只读、无 tools、无 memory、无 conversation history） | 比赛版暂不接入 |
| `octos.*` (turn/session/history) | ⚠️ 需要 contained apps policy 开启 + 用户授权 | 比赛版暂不依赖 |
| App 自己的 `AGENT.md` / `tools.json` / `skills` | ❌ App Hub 已能 gate，但当前 Shell pin 在旧 App Hub，可能拒绝新字段 | **不硬塞** |
| `glance.publish` | ❌ 当前 contained store app 还不能直接发布 | 设计好接口，等平台开放 |
| `octos.turn.start` / `octos.session.open` / `octos.session.history` / `octos.turn.interrupt` | ⚠️ 有条件可用（Shell 有 kernel + contained apps policy 开启 + 用户授权） | 比赛版暂不依赖 |

**结论：绝对不能为了"看起来 Agentic"就乱塞 `AGENT.md`、`tools.json`。如果比赛环境还是旧 pin，反而会把 App 搞坏。**

### 2.3 官方技术栈

| 组件 | 作用 |
|---|---|
| **OctoScript** | 意图驱动的脚本层，把意图结构化并生成 UI 数据 |
| **Makepad** | GPU 渲染引擎，跨平台（桌面/Android/Web），基于着色器语言 |
| **Octos / Octocode** | Agent 内核，支持多模型调度 |
| **OctoLoop** | 内外环执行分工（外环 Claude/Codex 做规划，内环 K3/MiniMax 干活） |
| **Autosize OS** | 纯 Rust 的 Agentic OS，作为宿主运行 |
| **Matrix 协议** | Robius 赛道的联邦通信 |
| **robrix2** | Robius 赛道的即时通讯客户端宿主 |

### 2.4 OctoLoop 双环设计

> **执行和判断，必须分开。**

- **内环 Agent**：把任务做完（octos 组织上下文、工具与执行）
- **外环人**：负责计划、观察和独立审查
  - 确定目标：要完成什么事
  - 批准范围：哪些操作可以做
  - 最终验收：结果对不对，由人判断，不由 Agent 自称

**结果不符合目标 → 退回，内环继续执行。**

## 三、竞品调研结论

### 3.1 中国市场

- **Grobit**：已完成完整家庭财务管理（资产负债表、五维健康、AI 报告、目标、行动追踪、情景模拟）
- **ReFi 算账**：动态家庭资产负债表 + AI 识别 + 财务规划

### 3.2 海外头部产品

- **Monarch Money**：Forecasting 功能——可以把收入+支出+账户+人生事件放在同一个长期模型里，模拟买房/生孩子/换工作/提前退休/Career Break
- **Origin**：2026 年 9 月推出 Proactive AI Advisor——主动检查财务状态（spending/cash flow/savings/investment/retirement/credit/housing/education/estate planning），发现值得关注的事情，生成 Actions
- **Copilot Money**：Money Assistant 做类似事情——AI 不只是搜索框，而是主动发现问题、提出建议，让用户 approve/dismiss

### 3.3 核心判断

**不要再做"另一个记账/理财 App"。** Monarch 已经把"人生事件→长期财务预测"做完整了，Origin 正在把"主动发现问题→Action"做完整了。

兜兜选择的位置：**中国家庭语境 + 安全余量 + 生活变化 + 决策记忆 + 主动守望。**

这五个连起来是一个有完整心智模型的 Agentic App，而不是一个功能少一点的理财工具。

### 3.4 兜兜和通用对话 AI 的本质区别

| 维度 | 通用对话 AI | 兜兜 |
|---|---|---|
| AI 对话 | ✅ | ✅ |
| 财务分析 | ✅ | ✅ |
| 情景推演 | ✅ | ✅ |
| **你的家庭状态** | 每次重新理解 | **持续维护** |
| **长期记忆** | 受限于 context | **结构化保存** |
| **你的"兜"是什么意思** | 没专门模型 | **核心模型** |
| 风险变化 | 用户主动问 | **持续监测** |
| 用户做决定以后 | 对话结束 | **继续观察结果** |
| **换模型以后** | 一切归零 | **你的兜还在** |

> **通用对话 AI 是一个很聪明的咨询者。**
> **兜兜是一个持续运行的家庭财务安全系统。**

## 四、产品哲学与设计决策

### 4.1 四条红线（决定不做什么，比决定做什么更重要）

1. **不评价你。** "这件事值不值得做？"——不判断。
2. **不替你决定。** "该不该做？"——不说。
3. **只告诉你变化。** "这件事会让你的安全缓冲从 29.6 个月变成 18.5 个月。"说完就停。
4. **记住你的选择。** 你上次说"先不买车"，它下次还会记得，并基于这个继续帮你看。

### 4.2 为什么不用通用对话 AI 做对比

讨论初期有人建议把兜兜定位为"比 ChatGPT 更懂财务的 AI"。
**决定：放弃这个定位。** 原因：
- 第一轮对话兜兜完全没理由比通用 AI 强
- 护城河不在"更聪明"，而在"持续维护你的家庭状态"
- 显式对比 ChatGPT/豆包/DeepSeek 会让评审觉得产品在做同一件事但做得不够好

改为："通用对话 AI 回答你的问题。兜兜记住你的生活，并一直帮你看着：这条路，还兜不兜得住。"

### 4.3 关键技术原则：Collection is code，judgement is the model

这是 OctoSense 官方明确强调的架构原则。

- **数据收集 / 数字计算 = 代码**（绝对不要让 LLM 算数字）
- **意图理解 / 表达判断 = 模型**

兜兜内部分工：
```
"我想买辆 30 万的车"
       ↓ AI 理解层
{ "event": "purchase", "amount": 300000 }
       ↓ 确定性代码（数字由程序算）
存款 80万 - 30万 = 50万 → 50万 ÷ 2.7万 = 18.5 个月
       ↓ Agent 判断（要不要提醒、怎么表达 trade-off）
UI / Action Card / 用户选择
```

### 4.4 欢迎用户把其他 AI 的建议拿来问兜兜

反直觉设计：
> 用户："通用对话 AI 说我可以拿 30 万创业。"
> 兜兜："这条建议本身没问题。但放到你的家庭模型里——你拿出这 30 万，安全缓冲从 15 个月降到 7.8 个月。"

兜兜不和通用大模型比聪明。它做的是**把你的家庭模型当作通用大模型没有的纵深**。

### 4.5 不做什么（产品边界锁死）

- ❌ 不推荐基金、股票、保险产品
- ❌ 不帮你决定该不该辞职/买房/生孩子
- ❌ 不记账、不连银行、不访问网络
- ❌ 不发明数字——所有月数都由程序按公式算
- ❌ 不做退休精算、资产配置、投资组合、财务健康评分
- ❌ 不做聊天机器人
- ❌ 不做通用大模型套壳

**不追加功能。** 先把"安全缓冲 + 情景推演 + 退路 + 记忆"这一条链做完整。然后再考虑别的。

## 五、产品架构：五层闭环

```
                 兜兜
                  │
        ┌─────────┼─────────┐
        ↓         ↓         ↓
     家庭状态   生活事件   我的决定
        │         │         │
        └────┬────┴────┬────┘
             ↓         ↓
          状态引擎   情景引擎
             │         │
             └────┬────┘
                  ↓
              安全状态
                  ↓
       ┌──────────┼──────────┐
       ↓          ↓          ↓
      稳定      值得留意     跌破底线
       │          │          │
       └──────────┼──────────┘
                  ↓
              Action
                  ↓
            用户选择
                  ↓
          Decision Memory
                  ↓
           下一次继续观察
```

### ① Memory — 记住你

事实和偏好，存在本机 `state.json`：
- 收入（来源数、月金额）
- 支出（房贷、必要生活费）
- 资产（可动用现金）
- 家庭成员（配偶、子女、父母）
- 安全线（你给自己留的底）
- 最大担忧（你最怕什么）

### ② Model — 理解你的"兜"

不是存"存款 = 80 万"，而是知道：
```
80 万现金 ÷ 必要月支出 2.7 万 = 29.6 个月
29.6 - 你设的底线 12 个月 = 余量 17.6 个月
```

"80 万"对兜兜没有意义，"29.6 个月 + 17.6 个月余量"才是它维护的模型。

### ③ Simulation — 看未来

同一个 Scenario Engine 处理所有事件：
- 买车 30 万
- 休息 6/18 个月
- 装修 / 旅行 / 买房 / 婚礼 / 支持家人 / 收入下降

以后新增事件，不需要给每个事件写一套完全不同的逻辑。

### ④ Monitor — 持续观察

App 打开时重新读 state.json 重新算。不是只显示上次的数字。

### ⑤ Action — 主动发现 + 三条退路

- 缓冲低于底线 → 红色告警 + "兜不住了"
- 缓冲被明显削薄（即使仍在底线之上）→ 主动提醒
- 三条退路：先留着现金 / 看看失业后的时间 / 等第二份收入

## 六、v0.1 实际做了什么（诚实清单）

代码在 `bundle/main.splash`（552 行 OctoScript），**已经在 OctoSense Shell 里跑过多次**。

### 已实现

| 功能 | 实现方式 |
|---|---|
| 听懂一句家庭情况 | 自然语言解析（正则提取数字） |
| 写入本机 `state.json` | `fs.write()` |
| 算当前安全缓冲 | 可动用现金 ÷ 必要月支出 |
| 算安全余量 | 缓冲 - 用户设的底线 |
| 生活费兜底估算 | 用户没说时按 1.2 万估算，UI 明确标注 |
| 三件大事推演 | 买车 / 休息 6 个月 / 休息 18 个月 |
| 跌破底线告警 | 缓冲 < 安全线 → 红色"跌破底线"标签 + 告警条 |
| 主动提醒 | 即使仍在安全线之上，削薄明显时也主动开口 |
| "先不辞，回到现在"退路 | `hold_cash()` 恢复原状态 |
| 决策轨迹 | `trail[]` 数组，"我记得你做过这些决定" |
| 数据只在本机 | manifest 只申请 storage，不访问网络 |

### 算式（由代码算，不由模型算）

```
可动用现金      = 存款
家庭必要月支出  = 房贷 + 生活费
安全缓冲月数    = 可动用现金 ÷ 家庭必要月支出
安全余量        = 安全缓冲月数 - 你设的底线
```

### 演示家庭

42 岁，已婚，一孩。月收入 4 万，房贷 1.5 万，存款 80 万，配偶暂无收入。最担心失业，希望家里至少撑 12 个月。

按这套数字：
- 现在：29.6 个月（稳定）
- 买车 30 万后：18.5 个月（少了 11.1，距离底线 6.5 个月）
- 休息 18 个月且收入变 0：11.6 个月（**低于底线**）

## 七、v0.1 已修复的 Bug

### fmt_num() 显示 bug（2026-10-03 修复）

**问题**：手写的 `fmt_num()` 对 >= 10 的数字会丢掉首位。
- `fmt_num(11.6)` → 返回 `"1.6"`（漏了十位的 1）
- `fmt_num(29.6)` → 返回 `"9.6"`（漏了十位的 2）
- `fmt_num(27.0)` → 返回 `"7.0"`（漏了十位的 2）

**原因**：函数试图用 `ip`（整数部分十位）和 `tenths`（取模十位）分别处理，但 `tenths = whole` 在 whole >= 10 时不会减到个位——逻辑有误。

**修复**：去掉 `ip`/`tenths` 拆分，改为简单的 `whole + "." + fw` 拼接。

**注意**：数字计算本身（`buffer_months()` / `cash_now()` / `necessary()`）完全正确。`state.json` 里存的值也是对的。只有显示层坏了。

## 十、给下一位 AI 的关键提醒

1. **不要为了"看起来 Agentic"硬塞当前还不能跑的平台能力。** 官方明确说当前 Shell pin 在旧 App Hub，新字段（`model`、`background`、`triggers`、`skills`）可能导致 App 被拒绝。
2. **数字永远由代码算，不由 LLM 编。** `fmt_num()` 修好了，但其他地方写新计算逻辑时也要遵守这个原则。
3. **v0.1 的 state.json 是空的会怎样？** 应用会进入 `missing_line()` 流程——显示追问卡片，不估算缺失字段。这是正确的空状态行为。
4. **演示户只有一户（42 岁已婚一孩）。** 这不是产品只服务这一户，而是需要一个足够具体、能跑完完整流程的样本。换数字时改 state.json 即可验证泛化能力。
5. **`living`（生活费）默认 1.2 万是兜兜估算的。** UI 已标注"可以改"。用户说真实数字后重算。
6. **三条退路中，"看看失业后的时间"（`look_jobless()`）和"等第二份收入"（`wait_second()`）函数已写但 UI 入口当前版本没有完全落地。** 这是 v0.2 的 TODO。
7. **`trail[]` 是决策轨迹，不是聊天记录。** 每次用户选择后追加一条：`"考虑过 XX，选择 YY"`。
8. **fmt_num() 修好了但逻辑仍然是手写的**。以后如果要支持更多小数位或千分位，建议重写，但现在 1 位小数够了。
